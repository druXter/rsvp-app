## Architecture

Next.js App Router app (Next 16, React 19) that runs one or more independent RSVP events — optionally grouped into multi-date event series — under dynamic slugs. SQLite via Prisma is the only datastore; there is no separate API backend — all writes go through Next.js Server Actions.

**Data model** (`prisma/schema.prisma`): `User`/`Session` (auth, see below) plus the event-domain models. `Event` (a single date/"Termin") optionally belongs to an `EventSeries` via nullable `seriesId`; when `seriesId` is null it's a fully standalone event (the default, unchanged flow). `Participant` is a guest's identity (name, email, phone, dietaryOption, allergies, verification state, `editToken`) — for a standalone event a `Participant` exists 1:1 with its one `Rsvp`, but within a series ONE `Participant` is reused across that series' multiple `Rsvp` rows so contact/profile data is only collected once. `Rsvp` holds only the per-Termin answer (isAttending, isOnWaitlist, drinksAlcohol, bringingItem, additionalInfo/declineReason, its `persons`) and is unique per `(eventId, participantId)`. `Event.formConfig` is a JSON string toggling which optional fields a guest form shows; for a series Termin only its per-Termin keys (askAlcohol, askBringingItem) are meaningful — the shared profile questions (askEmail/askPhone/askDiet/askAllergies) live on `EventSeries` instead and both pages that render a series form merge the two into one config object before passing it to `RsvpForm`. `Participant.editToken` is the one link a guest uses to revisit any of their answers; for a series it doubles as the key that carries their profile forward when they open a *new* Termin they haven't answered yet (`existingParticipant` found, but no `existingRsvp` for that specific event — see `submitRsvp`).

**Effective settings resolve through the series when present**: `requireVerification`, `isGuestListVisible`, and `eventPin` all live on both `Event` and `EventSeries`; whenever `event.seriesId` is set, the `EventSeries` value is authoritative and the same-named `Event` column is ignored/inert. Every place that branches on these (capacity/verification logic in `submitRsvp`, `triggerWaitlistPromotion`, the admin guest table, the CSV export, the public event page) computes `const requireVerification = event.series ? event.series.requireVerification : event.requireVerification` (or the PIN/guest-list equivalent) rather than reading the `Event` column directly — do the same in new code.

**Server Actions are the backend**, split by audience:
- [app/actions.ts](app/actions.ts) — public guest-facing actions: `submitRsvp` (create/update a `Participant` + `Rsvp` for one Termin — works unchanged for both standalone events and series Termine) and `verifyEventPin` (branches on whether the form posted an `eventId` or a `seriesId`).
- [app/admin/actions.ts](app/admin/actions.ts) — admin-only actions: standalone event CRUD (`createEvent`/`updateEvent`/`deleteEvent`, untouched by the series feature), series CRUD (`createEventSeries`/`updateEventSeries`/`deleteEventSeries`/`addTerminToSeries`), plus `sendReminder`, `resendVerificationEmail`, `promoteFromWaitlist`, `updateAdminRsvp` (writes `Participant` and `Rsvp` fields separately), `loginUser`/`logoutUser`/`createUser`, etc. Every admin action must independently call `requireUser()` (throws if not logged in) *and* verify ownership of whatever it's touching — there is no middleware enforcing this centrally, and route pages (e.g. [app/admin/page.tsx](app/admin/page.tsx)) do their own `getCurrentUser()` + `redirect('/admin/login')` + ownership check.

**Routing**: standalone events live at `/[slug]`; if that slug turns out to belong to a series Termin, the page redirects to the canonical `/reihe/[seriesSlug]/[terminSlug]` (preserving `?token=`) so series-only settings (PIN, merged form config, shared guest list toggle) can't be bypassed via the flat URL. A series overview lives at `/reihe/[seriesSlug]` (lists its Termine, gated by the series PIN) and each Termin's form at `/reihe/[seriesSlug]/[terminSlug]`. **Archive:** `isArchived()`/`splitArchived()` in [app/lib/event-date.ts](app/lib/event-date.ts) are the one definition of "past" for series Termine (48 h after `date`, never while `datePending`): the guest-facing lists (`/reihe/[seriesSlug]`, `/mein-konto`) drop archived Termine, the admin series page (`/admin/series/[id]`, tab "Termine") renders them in a collapsed "🗄️ Archiv" (newest first); the dashboard's series cards only show the next upcoming Termine. It's display-only — the Termin page itself stays reachable via its personal link, and nothing is deleted before the retention cron. Standalone events are unaffected.

**Auth is per-user and multi-tenant**: `User` (email + bcryptjs `passwordHash`, nullable since federation — see "Account security & federation" below) and `Session` (an opaque random `token`, DB-looked-up per request, plus `expiresAt`; the DB stores only its SHA-256 hash) live in the schema; the `__Host-session` httpOnly cookie (`session_token` in dev over http) carries only the token — never a user id or role — so a tampered cookie can't impersonate anyone (see [app/lib/auth.ts](app/lib/auth.ts)'s `getCurrentUser()`/`requireUser()`, and `loginUser`/`logoutUser` in [app/admin/actions.ts](app/admin/actions.ts)). There is no public signup: the only way to create a `User` is already being logged in and using `createUser` (the "+ Nutzer anlegen" page), or the one-off [create-user.js](create-user.js) script for the very first account. `Event` and `EventSeries` each carry a required `ownerId`; every admin page and Server Action that reads or mutates one must both scope the query by `ownerId: user.id` (list views) *and* re-check ownership after fetching by id (detail/edit/delete/admin-action endpoints) — Next.js has no middleware enforcing this centrally, so a new admin route/action must do both checks itself or it silently leaks or corrupts another tenant's data. A series Termin's `ownerId` is always copied from its parent `EventSeries.ownerId` at creation time (`addTerminToSeries`), not set independently. `PushSubscription` also carries a `userId`; [app/lib/push.ts](app/lib/push.ts)'s `sendPushToUser(userId, ...)` only ever notifies that one user's devices, keyed off `event.ownerId` at the `submitRsvp` call site — never a global broadcast. A standalone event's `eventPin` gates its page via an `event_pin_<eventId>` cookie; a series' `eventPin` gates every one of its Termine via a single `series_pin_<seriesId>` cookie, checked in both [app/[slug]/page.tsx](app/[slug]/page.tsx) and the `app/reihe/` pages — these are unrelated to user auth and still just gate guest-facing pages.

**Roles & shared (Moderator) access**: `User.role` is one of `ADMIN` / `CREATOR` (the default — every account before this feature behaves exactly like a Creator) / `MODERATOR`. [app/lib/permissions.ts](app/lib/permissions.ts) is the single place that resolves rights and must be used instead of a raw `ownerId` comparison: `isOwnerOrAdmin(user, ownerId)` (Admins bypass ownership entirely — "alle Rechte" on every tenant's data) for owner-only actions (create/update/delete Event/EventSeries, `addTerminToSeries`, `updateSeriesTermin`, `sendReminder`, `shareResource`/`unshareResource`), and `hasEventModeratorOrAbove(user, event)` for guest-list-scoped actions a Moderator is also allowed to perform (`updateAdminRsvp`, `deleteRsvp`, `promoteFromWaitlist`, `toggleAttendance`, `resendVerificationEmail`, the `/admin/checkin/[rsvpId]` page, and the `/api/export` CSV route). The `ResourceAccess` model (`userId` + exactly one of `eventId`/`seriesId`) is how an owner or Admin grants a specific user Moderator-level access to one Event or to a whole EventSeries (which then covers every one of its Termine automatically — `hasModeratorAccess` checks both the direct `eventId` and, if the event belongs to a series, the series' `seriesId`); managed via `shareResource`/`unshareResource` and the [ShareAccessPanel](app/admin/share-access-panel.tsx) shown on the Event edit page and the Series edit page. A Creator who only has Moderator access to someone else's resource cannot re-share it further — `shareResource` itself requires `isOwnerOrAdmin`. `createUser` additionally gates which role the *requester* may hand out: only an Admin may create another `CREATOR` or `ADMIN` account (`app/admin/create-user/page.tsx` only renders the role `<select>` for Admins); a Creator can only create `MODERATOR` accounts, and a `MODERATOR` cannot call `createUser` at all — this keeps the number of independent tenants (Creators) under the sole control of Admins. The admin dashboard ([app/admin/page.tsx](app/admin/page.tsx)) reflects all of this: Admins see every account's Events/Reihen (with the owner's e-mail), everyone else sees their own plus those shared via `ResourceAccess` (badge "freigegeben"); on the event page `loadAdminEvent` (app/admin/events/[id]/event-access.ts) resolves `isOwner`, which hides the Einstellungen tab and the reminder/payment-reminder/invitation-mail buttons for moderators. Deleting an Event or EventSeries must also delete its `ResourceAccess` rows first (same manual-cascade convention as Rsvp/Participant cleanup) or the FK delete fails.

**Admin-only user management** ([app/admin/users/page.tsx](app/admin/users/page.tsx), gated by `user.role !== 'ADMIN'` → `redirect('/admin')`) lists every account with its role and owned-resource counts, and lets an Admin change another account's role (`updateUserRole`) or delete it entirely (`deleteUser`, cascading through that user's owned Events/EventSeries/Rsvps/Participants/PushSubscriptions/Sessions and any `ResourceAccess` rows either granted to or by them — the same manual-cascade pattern as `deleteEventSeries`). Both actions categorically refuse to touch any account whose `role` is `ADMIN` — including the caller's own row — so an Admin can never demote or delete another Admin (or themselves) through the UI; the only way to change an Admin account's role is the server-side `set-role.js` script. This is a deliberate safety rail against ever losing the last working Admin login, not an oversight — don't relax it without the user explicitly asking.

**Guest-side login ("Nutzer" accounts)**: a `GuestUser` (email + bcryptjs `passwordHash`, plus the shared profile: `name`/`phone`/`dietaryOption`/`allergies`/`isVerified`) is a completely separate concept from the admin-side `User`/`Role` — it has its own session model (`GuestSession`, a `__Host-guest-session` httpOnly cookie — `guest_session_token` in dev — resolved via [app/lib/guest-auth.ts](app/lib/guest-auth.ts)'s `getCurrentGuestUser()`/`requireGuestUser()`) so a guest session can never be confused with or escalate into an admin session. A `GuestUser` can belong to multiple `EventSeries` at once via the `GuestUserSeries` join table (n:m, not a single field) — membership is created three ways: self-registration on `/reihe/[seriesSlug]/registrieren` (gated behind the same series PIN cookie as the rest of that series; creates the `GuestUser` plus one `GuestUserSeries` row for that series and emails a verification link via `sendGuestVerificationEmail`; `loginGuestUser` refuses to log in an unverified account), a Creator/Moderator of that series adding an *existing* `GuestUser` by email (`addGuestUserToSeries`/`removeGuestUserFromSeries` in [app/admin/actions.ts](app/admin/actions.ts), gated by `hasSeriesModeratorOrAbove`, rendered via [GuestMembersPanel](app/admin/guest-members-panel.tsx) on the series edit page — this action never creates a new `GuestUser`, only links an existing one), or automatically the first time a logged-in guest answers any Termin of a series they weren't already a member of (`submitRsvp` upserts the `GuestUserSeries` row). The profile lives centrally on `GuestUser`, not per-`Participant`: `Participant.guestUserId` (nullable) links a series' `Participant` row back to the owning `GuestUser`, and `submitRsvp` in [app/actions.ts](app/actions.ts) resolves identity via `getCurrentGuestUser()` whenever no `editToken` is present and the Termin belongs to a series — finding (or lazily creating, seeded from the central profile) that series' `Participant` for this guest — and afterwards writes the submitted name/phone/dietaryOption/allergies *back* onto `GuestUser` so every other series membership immediately reflects the change (also `updateGuestProfile` in [app/mein-konto/actions.ts](app/mein-konto/actions.ts), which `updateMany`s every linked `Participant` when the guest edits their profile directly on `/mein-konto`). `finalEmail`'s fallback chain in `submitRsvp` explicitly includes `guestUser?.email` — without it, a Termin whose `askEmail` is off never puts anything in `emailInput`, so a logged-in, already-verified guest's known email would otherwise never make it onto their `Participant` at all (a real bug fixed once already: the field being *optional to ask* must not mean the already-known, already-verified value gets silently dropped). That fallback only ever fires when `submitRsvp` actually resolves `guestUser` (gated by `!editToken`), so `RsvpForm` must only ever embed its hidden `editToken` input when the `participant` it was handed truly came from a URL `?token=` — both call sites pass `usedUrlToken={!!token}` for exactly this reason. A `Participant` resolved via an active guest session (no `?token=` in the URL) always already has a real `editToken` of its own too (e.g. for the delete-my-data button), so naively embedding it unconditionally (the pre-fix behavior) round-trips a non-empty `editToken` on every submission from a *returning* guest — which makes `submitRsvp` treat the request as the anonymous token flow and skip `getCurrentGuestUser()` entirely, silently defeating the `guestUser?.email` fallback above for anyone who already has a `Participant` in that series (a second real production bug, found only after the first fix didn't actually resolve the user's report — don't reintroduce the unconditional hidden `editToken` input). This keeps the pre-existing anonymous `editToken` flow from #10 completely untouched — a guest without an account still works exactly as before, and `existingParticipant`'s `guestUserId` is preserved even when someone answers via an old token link while not currently logged into their guest session. `/mein-konto` (guarded by `getCurrentGuestUser()` → `redirect('/mein-konto/login')`) lists every series membership with its Termine and each one's current answer status, linking straight into `/reihe/[seriesSlug]/[terminSlug]` **without** a `?token=` — the Termin page resolves the guest session server-side instead. This Reihen/Termine list is deliberately the *first* thing on the page — `updateGuestProfile`'s "Deine Angaben" form lives in a `<details>` element below it, collapsed by default, since it's only relevant occasionally (first setup, or an address/allergy change) rather than on every visit; password/email/account-deletion live one level further out, on the separate `/mein-konto/account` sub-page reached via a single "⚙️ Konto-Einstellungen" button in the header, not inline on the dashboard. The shared PWA manifest ([app/manifest.ts](app/manifest.ts)) has `start_url: '/'` (not `/admin`) specifically so it works for both an installed admin dashboard and an installed guest "Mein Konto" shortcut; the landing page ([app/page.tsx](app/page.tsx)) offers both entry points.

**Client API for self-built apps** (`app/api/v1/`): a small REST surface so a guest can build their own client (the first ask was a WatchOS app). It exists because Server Actions are unreachable from a native app — they speak the RSC protocol, not HTTP-with-a-token. Authentication is a `GuestApiToken` (schema.prisma) presented as `Authorization: Bearer rsvp_…` and resolved by `getGuestUserFromApiToken()` in [app/lib/api-auth.ts](app/lib/api-auth.ts); only the SHA-256 hash is stored (same as `Session`/`GuestSession` since the token-hash migration — an API token is long-lived and gets typed into third-party software, so a DB leak must not hand over working keys), and the plaintext is shown exactly once via the one-minute `new_api_token` cookie that `createApiToken` sets. The API is deliberately **guest-side only** — a token can never reach admin data — and covers `GET /api/v1/me`, `GET /api/v1/termine` (the account's own series, upcoming Termine, own answers) and `POST /api/v1/termine/[eventId]/antwort`. Writing is restricted to Termine of a series the account is a `GuestUserSeries` member of; standalone events are rejected, since without a series there is no account identity and a new anonymous `Participant` would be created instead. Name and profile fields are never settable through the API — they always come from the `GuestUser`, so a client can answer but cannot overwrite the central profile. Deleting a `GuestUser` must delete its `GuestApiToken` rows first (`deleteGuestAccount` and the `cron/cleanup` inactivity sweep), same manual-cascade rule as everywhere else.

**Admin API (read-only)** (`app/api/v1/verwaltung/`): `UserApiToken` (own table, prefix `rsvpv_`, SHA-256 hash only, created/revoked via `createAdminApiToken`/`revokeAdminApiToken` on `/admin/account`, plaintext shown once via the one-minute `new_admin_api_token` cookie scoped to `/admin`) resolved by `getUserFromApiToken()` in [app/lib/api-auth.ts](app/lib/api-auth.ts). A token carries no rights of its own: every route re-checks the account's *current* rights through [app/lib/admin-api.ts](app/lib/admin-api.ts) — `accessibleEventsWhere(user)` (ADMIN all, else own + `ResourceAccess` events/series, same as the dashboard) for lists and `loadApiEvent` (`hasEventModeratorOrAbove`) for one event, 404 alike for missing and forbidden. Endpoints: `/me`, `/termine` (from two days ago, `?alle=1` all; `responses` and menu courses, no names), `/termine/[eventId]/kueche` (`kitchenForApi` over `loadKitchenReport`: counts per course, persons with name/menu/table). `kitchenForApi` deliberately drops per-person `dietaryOption`/`allergies` (Art. 9 data must not flow into third-party software; only `personsWithAllergies`) — keep it that way. No write endpoints; a guest token never resolves here and an admin token never on the guest API (separate tables). Tests: [tests/e2e/admin-api.spec.ts](tests/e2e/admin-api.spec.ts).

**One RSVP code path**: the answer logic (identity resolution, capacity/waitlist, verification, confirmation mail vs. push) lives *only* in `performRsvpSubmission()` in [app/lib/rsvp-submission.ts](app/lib/rsvp-submission.ts). `submitRsvp` in [app/actions.ts](app/actions.ts) is now just a FormData adapter over it, and the API route is a JSON adapter — so the two can never drift apart. The caller passes the identity it established (cookie session for the form, API token for the API) as `guestUserCandidate`; whether that identity is actually used is still decided inside `performRsvpSubmission` by the unchanged `!editToken && event.seriesId` condition. A caller must therefore never derive that argument from client-supplied data — and it must never become a parameter of the exported Server Action itself, since Server Actions are callable from the client and an attacker could then simply assert someone else's identity.

**Capacity / waitlist logic** has one rule for every path: `hasRoom(limits, rsvps, categoryId, excludeRsvpId, seats)` in [app/lib/tickets.ts](app/lib/tickets.ts) (the Termin's `maxCapacity` *and* the ticket category's `capacity` must both have room for all `seats` of the answer; seats count persons, see below; waitlisted and declined rows hold nothing). `performRsvpSubmission` uses it to decide whether a new/edited answer lands on the waitlist (an existing fixed seat in the same category is kept; switching a fixed seat into a full category throws `RsvpInputError` instead of silently swapping it for the waitlist), `verifyParticipantByToken` uses it when a verified waitlisted answer is re-checked, and `fillFreeSeats(eventId)` in [app/lib/waitlist.ts](app/lib/waitlist.ts) is the single place that promotes waitlisted guests (FIFO by `createdAt`, the first one *for whom* there is room — a full category never blocks another category's queue; only verified participants if the effective `requireVerification` is on; with no limits at all everyone is promoted). Call it whenever a fixed seat may have freed up or limits grew: guest declines or changes category, admin edits/deletes/cancels, `updateEvent`/`updateSeriesTermin` (via `applyTicketing`). It sends `sendWaitlistPromotedEmail` + confirmation (respecting `disableConfirmationEmails`), swallows mail errors, sets the payment due date and notifies linked tools itself. Capacity is always per Termin, never shared across a series. The manual "Zulassen" (`promoteFromWaitlist` admin action) deliberately ignores limits.

**Double opt-in**: verification lives on `Participant`, not `Rsvp` — so once a guest verifies, that status covers every Termin of their series, not just the one that triggered it. When the effective `requireVerification` is true, a new-or-changed email puts the `Participant` in an unverified state (`isVerified: false`, fresh `verifyToken`, reused if one is already pending) and sends a verification email instead of a confirmation; [app/verify/page.tsx](app/verify/page.tsx) shows a confirm button, and only its click (`verifyParticipantByToken` in [app/lib/participant-verification.ts](app/lib/participant-verification.ts)) consumes the `verifyToken`, flips `isVerified`, and then re-runs the capacity check and fires the confirmation/waitlist email for *every* attending `Rsvp` that `Participant` currently has pending (usually one, but can be more if they answered multiple not-yet-verified Termine before clicking the link).

**Public guest list** ([app/[slug]/page.tsx](app/[slug]/page.tsx) and the `app/reihe/` Termin page): when the effective `isGuestListVisible` is on, the page does a `select`-scoped Prisma query (pulling only `participant.name` from the relation) that must never include `email`, `phone`, or `allergies` — this is a deliberate privacy boundary, not an oversight, so preserve the explicit field allowlist when touching this query. It always lists guests for one specific Termin, never combined across a series.

**Email** ([app/lib/mail.ts](app/lib/mail.ts) loads data and sends, [app/lib/mail-templates.ts](app/lib/mail-templates.ts) holds the content, pure): every mail is built from `suite-kit/web` building blocks (`renderMail` → HTML and text from the same content, the suite's single mail template, design rules in `../suite-kit/docs/DESIGN.md` "Mails") - never hand-written HTML. The blocks escape every value (guests can sign up with someone else's address, so unescaped HTML would reach a third party's inbox from our DKIM-signed sender) and only allow http(s)/mailto/tel/cid links; the subject stays raw. Preview all mails with sample data: `npx tsx scripts/mail-preview.ts` (writes `.e2e/mail-preview/`), `--send <address>` (with `--env-file=.env`) mails the full confirmation.  all guest emails (confirmation, verification, waitlist, waitlist-promoted, reminder, event-updated) go through nodemailer using a single transporter built from `SMTP_*` env vars, and now take `participant` and `rsvp`/`event` as separate arguments (identity vs. per-Termin answer) rather than one flat object. Confirmation emails attach a generated `.ics` file (via the `ics` package) built from `Event.date`/`duration` in UTC, using the shared `buildIcsAttachment()` helper, which pins a stable `uid` (derived from `event.id`, not a random one) and a `sequence` number (`Event.icsSequence`) on every generated file — this is what lets a calendar app (Google/Apple/Outlook) recognize a later-sent .ics for the same event as an *update* to an already-saved entry instead of creating a duplicate. Every guest email embeds the personal link via `personalEventLink()`, which points at `/reihe/[seriesSlug]/[slug]` for a series Termin and `/[slug]` otherwise; confirmation/waitlist emails for a series Termin also add a link to the series overview so the guest can answer other dates.

**Urgent event-change notification**: an Admin/Creator editing an already-published `Event` or series Termin (`updateEvent`/`updateSeriesTermin` in [app/admin/actions.ts](app/admin/actions.ts)) can optionally notify everyone who already answered "ja" (including waitlisted guests) that something relevant changed. `diffEventFields()` is the single place that decides what counts as "relevant" — title, date, duration, location, description — comparing the pre-edit `existingEvent` against the submitted form values; a non-empty result both (a) increments `Event.icsSequence` unconditionally (so the calendar data's own revision count stays accurate even on a save where the admin chose not to notify) and (b) is the prerequisite for actually sending anything. The "Teilnehmende benachrichtigen" checkbox itself only ever sends when *both* something relevant changed *and* the admin explicitly checked it — nothing goes out automatically just because a field changed, and the checkbox (`app/admin/notify-guests-toggle.tsx`, a client component watching the surrounding form's `input` events via `formId`) only renders at all once at least one watched field actually differs from its original value, so it can never be checked when there's nothing to send. When checked, `notifyAttendeesOfChange()` queries every `Rsvp` with `isAttending: true` for that one Termin (capacity/attendance is still always per-Termin, series or not), applies the same effective-`requireVerification` resolution as everywhere else (`event.series ? event.series.requireVerification : event.requireVerification`) to skip still-unverified participants, and sends `sendEventUpdatedEmail()` **and** `sendEventChangedPush()` to the rest — see "Guest push notifications" below for the push side.

**Reminders**: manual send is the `sendReminder` admin action; automatic send is the unauthenticated `GET /api/cron/reminders?secret=CRON_SECRET` route ([app/api/cron/reminders/route.ts](app/api/cron/reminders/route.ts)), intended to be polled by an external scheduler (e.g. Uptime Kuma). It computes a per-event trigger date (`date - reminderDays`) and sets `reminderSent: true` once processed, so it is idempotent per event — don't remove that guard when editing. Reminders are always per-Termin, series or not, since `autoReminder`/`reminderDays`/`reminderSent` live on `Event`.

**Automatic data retention cleanup** ([app/api/cron/cleanup/route.ts](app/api/cron/cleanup/route.ts), same unauthenticated-but-secret-gated Uptime-Kuma-polled shape as the reminders route, meant to run daily rather than hourly) implements the storage-limitation periods documented in `/datenschutz` point 16 (Speicherdauer) — this is the one place in the app that runs unattended, irreversible bulk deletion, so preserve its exact ordering if you touch it: (1) delete every `Event` whose `date` is more than `EVENT_RETENTION_MONTHS` (18) in the past, entirely — not just its guests' data, the `Event` row itself too — cascading its `Rsvp`s and any `ResourceAccess` sharing it first (same FK-order requirement as `deleteEvent`); this applies identically to standalone events and series Termine. (2) Only *afterwards* sweep for now-orphaned `Participant` rows (`rsvps: { none: {} }`) and delete those — this is what correctly handles a series-shared `Participant`: deleting one old Termin's `Rsvp` does *not* delete the `Participant` if it still has a surviving `Rsvp` on a more recent Termin of the same series, so an active weekly Reihe's participants are never wiped out just because one past Termin aged out. (3) Independently, delete every `GuestUser` whose `lastLoginAt` is more than `GUEST_ACCOUNT_INACTIVITY_YEARS` (2) in the past, cascading its `Participant`/`Rsvp` rows (across *all* series, not just one), `GuestUserSeries` memberships, and `GuestSession`s — deliberately scoped to `GuestUser` only, never the admin-side `User` model, since a Creator/Moderator/Admin account represents an ongoing tenant identity that shouldn't vanish just from being unused for a while. `GuestUser.lastLoginAt` defaults to `createdAt` at creation and is refreshed on every successful `loginGuestUser`, so an account that registered but never logged in again starts its inactivity clock from registration, not from a login that never happened.

**CSV export**: `GET /api/export?eventId=...` ([app/api/export/route.ts](app/api/export/route.ts)) streams a semicolon-delimited, UTF-8 BOM-prefixed CSV of one Termin's guest list, joining in `participant` for name/email/phone/dietaryOption/allergies (unlike the public guest list, this includes them). **Impressum placeholders**: [app/impressum/page.tsx](app/impressum/page.tsx) reads `IMPRESSUM_NAME`/`IMPRESSUM_STREET`/`IMPRESSUM_ZIP`/`IMPRESSUM_CITY`/`IMPRESSUM_EMAIL`/`IMPRESSUM_PHONE` from env, falling back to bracketed placeholder text (`[Dein Vorname] [Dein Nachname]`, etc.) when unset — this keeps real personal data out of the repo (only placeholders live in `.env.example`) while a deployment's own untracked `.env` supplies the real values. **Web push**: deliberately built without `next-pwa` (known Turbopack-compatibility issues) — [app/manifest.ts](app/manifest.ts) uses Next's native Metadata File Convention (auto-linked into `<head>`, no manual `<link rel="manifest">` needed), and [public/sw.js](public/sw.js) is a hand-written, minimal service worker that only handles `push`/`notificationclick` (no offline asset caching, not needed here). The app icon itself is [app/icon.svg](app/icon.svg) — also picked up automatically by the Metadata File Convention (served at `/icon.svg`, auto-linked as `<link rel="icon">`) — plus a matching [app/favicon.ico](app/favicon.ico) (16/32/48px, built by combining `sharp`-rasterized PNGs via the `png-to-ico` package, installed temporarily with `--no-save` the way `playwright-core` is for testing — not a project dependency) for browsers/crawlers that request `/favicon.ico` directly, and `public/icons/icon-{192,512}.png` (same `sharp` rasterization) referenced from the manifest's `icons` array for PWA install-icon quality on platforms that don't accept SVG there, plus `public/icons/icon-maskable-{192,512}.png` (`purpose: 'maskable'`, rasterized from [public/icons/icon-maskable.svg](public/icons/icon-maskable.svg)) — Android lays its own mask shape over the icon, and without a maskable variant the round, transparent-cornered `icon.svg` shows a rim of background around the circle; the maskable source is the same motif on a full-bleed background, kept inside the safe zone (radius 40 % of the edge, 204.8 px at 512). Regenerate all of these together (including the maskable SVG) if the icon ever changes — a mismatched favicon.ico/icon.svg/manifest icon set is the kind of thing nobody notices until a user points it out. [app/lib/push.ts](app/lib/push.ts)'s `sendPushToUser()` no-ops silently whenever `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` aren't all set, so the feature is fully optional infrastructure — nothing else in the app depends on it. `PushSubscription` rows belong to one `User` — a brand-new `Rsvp` (not edits) in `submitRsvp` pushes only to the event owner's devices (`sendPushToUser(event.ownerId, …)`); expired ones (HTTP 404/410 from the push service) are pruned automatically on send failure. [app/admin/push-subscribe-button.tsx](app/admin/push-subscribe-button.tsx) registers the service worker once on mount (not inside the click handler) specifically so `handleSubscribe` only needs one `await navigator.serviceWorker.ready` before calling `pushManager.subscribe()` — spreading more awaited steps between the click and the `subscribe()` call risks the click's transient "user activation" expiring first, which makes the browser hang the subscribe call indefinitely with no error (reproduced during testing; keep this ordering when touching this file).

**Guest push notifications**: a parallel, independent push system for guests (reminders and urgent event changes), added after the admin-only one above and deliberately *not* built on top of it — an admin push subscription is tied to the admin-side `User`, but a guest answering an RSVP usually has no account at all (see "Guest-side login" — `GuestUser`/`mein-konto` is opt-in), so guest push had to hang off the identity every guest already has regardless of login: the `Participant`. `ParticipantPushSubscription` (schema.prisma) mirrors `PushSubscription`'s shape (`endpoint`/`p256dh`/`auth`) but keys off `participantId` instead of `userId`; `subscribeParticipantToPush`/`unsubscribeParticipantFromPush` (public actions in [app/actions.ts](app/actions.ts), alongside `submitRsvp`/`deleteMyParticipantData`) authorize purely by knowledge of a valid `editToken` — same anonymous-self-service security model as `deleteMyParticipantData`, no login required. Because a series' `Participant` is shared across all its Termine, subscribing once from any one Termin's page covers reminders/changes for every Termin of that series, not just the one the guest subscribed from. [app/[slug]/push-subscribe-toggle.tsx](app/[slug]/push-subscribe-toggle.tsx) is the guest-facing mirror of `app/admin/push-subscribe-button.tsx` (same service-worker-registered-on-mount pattern, same `public/sw.js`, same VAPID public key from `process.env.VAPID_PUBLIC_KEY` threaded down from both `app/[slug]/page.tsx` and the `app/reihe/` Termin page as a `vapidPublicKey` prop through to `RsvpForm`) and is rendered next to `DeleteMyDataButton` everywhere that component already appears with a real `editToken` in scope, *except* the decline and email-verification-pending screens — a guest who said no doesn't need reminders, and the verification-pending screen is transitional (they'll see the toggle on their next visit once verified). [app/lib/push.ts](app/lib/push.ts)'s `sendPushToParticipant()` is `sendPushToUser()`'s guest-side twin (same VAPID/no-op-if-unconfigured guard, same automatic pruning on HTTP 404/410); `sendReminderPush()` and `sendEventChangedPush()` sit on top of it as the push equivalents of `sendReminderEmail()`/`sendEventUpdatedEmail()`, built the same way `mail.ts` builds email content — both link out via the same `personalEventLink()` exported from `mail.ts`, so a tap on the notification and a click in the matching email land on the exact same page. Both are called *alongside*, not instead of, their email equivalents, at every existing trigger site (the manual `sendReminder` admin action, the `/api/cron/reminders` route, and `notifyAttendeesOfChange` for the "Teilnehmende benachrichtigen" checkbox) — push never gates on whether the participant has an email address at all, only email-sending does. Any code path that deletes a `Participant` (`deleteMyParticipantData`, `deleteGuestAccount`, the `deleteEventSeries`/`deleteUser` admin actions, and the retention `cron/cleanup` route's orphaned-participant sweep) must delete its `ParticipantPushSubscription` rows first, same manual-cascade-order requirement as `Rsvp`/`Participant` everywhere else in this codebase. `sendConfirmationPush()` is the one exception to the "alongside, not instead of" rule above: it is sent *instead of* `sendConfirmationEmail()` when `GuestUser.disableConfirmationEmails` is set — a per-account opt-out a guest sets themselves on `/mein-konto/account` (`updateConfirmationEmailPreference` in [app/mein-konto/actions.ts](app/mein-konto/actions.ts)), for people who read the confirmation in the installed PWA anyway. Enabling it is refused server-side unless at least one `ParticipantPushSubscription` exists across that account's `Participant` rows (the checkbox is also rendered disabled then), so nobody can silence their only channel; turning it back off is always allowed. `submitRsvp`'s private `shouldSuppressConfirmationEmail()` resolves the flag via `participant.guestUserId` at both `sendConfirmationEmail` call sites (the normal confirmation branch and the waitlist-promotion branch) — anonymous `editToken` guests have no `guestUserId` and therefore always keep the email. It deliberately covers *only* the confirmation mail: verification, waitlist, reminder and event-changed emails are unaffected, since the first is security-relevant and the rest already have push sent alongside them.

**External poll link (abstimmungstool integration)**: `Event.pollUrl`/`pollLabel` (both nullable, per-Termin like `maxCapacity`/`enableCheckin` — set independently even within a series) optionally point a Termin at a poll in the separate, independently-developed `abstimmungstool` project (sibling directory `/home/alex/abstimmungstool`, its own repo/deployment — never merge its code into this one). The session-independent part (attendance lookup, signing, appending `?verify=`) lives in `personalPollLink()` ([app/lib/poll-link.ts](app/lib/poll-link.ts)), shared with the client-API route `GET /api/v1/termine/[eventId]/abstimmung` (API token instead of session: own series only, verified account only, returns `{ url, label, verified, attending, expiresAt }` with `no-store`; `GET /api/v1/termine` only exposes `poll: { label } | null`, never the URL); `GET /api/v1/termine` also returns `responses` (counts via `summarizeEvent`, no names) only for series with `isGuestListVisible`, else null — the one deliberate exception to "the API never returns other guests' data" — used by the Discord bot in `~/mittwoch-bot`. `POLL_VERIFICATION_SECRET` must be byte-for-byte identical to abstimmungstool's `RSVP_VERIFICATION_SECRET` (shared HMAC key, generate with `openssl rand -hex 32`). Every message of this coupling (click token `poll-access`, webhook `poll-attendance`, result `poll-result`, `poll-date-*`, `survey-access`, `assembly-*`) uses the suite format `{ typ, aud, ...fields, iat, exp }` via `signForPollTool`/`verifyFromPollTool` in [app/lib/poll-verification.ts](app/lib/poll-verification.ts) (built on `signLinkMessage`/`verifyLinkMessage` from `suite-kit`): `aud` is the recipient's origin (the click token's is the origin of `pollUrl`), incoming messages need `aud` = our `BASE_URL` origin and at most 15 min validity (`survey-access` is the documented exception, 12 h). Fixed check messages in `tests/unit/poll-verification.test.ts` and abstimmungstool's `tests/unit/rsvp-verification.test.ts` must stay identical — change both sides in one go; nothing in either app validates the *other* app's availability, so a wrong/missing shared secret just silently degrades to "link works, no auto-verification" rather than breaking anything.

**Mail links never act on GET**: link scanners of mail providers (Defender Safe Links, Mimecast, …) fetch links automatically, some in a real browser. Otherwise a scanner would confirm an account registered with, or switched to, someone else's address — and that address then counts as proven (e.g. the abstimmungstool verification token). Password reset already worked this way. **Password reset (both login systems)**: `User.resetToken`/`resetTokenExpiresAt` and `GuestUser.resetToken`/`resetTokenExpiresAt` (nullable, same one-token-at-a-time shape as `Participant.verifyToken`) each power their own independent self-service "Passwort vergessen" flow — `requestPasswordReset`/`resetPassword` (`/admin/forgot-password`, `/admin/reset-password`) in [app/admin/actions.ts](app/admin/actions.ts) for admin-side `User` accounts, and `requestGuestPasswordReset`/`resetGuestPassword` (`/mein-konto/forgot-password`, `/mein-konto/reset-password`) in [app/mein-konto/actions.ts](app/mein-konto/actions.ts) for `GuestUser` accounts — deliberately two separate implementations rather than a shared one, mirroring the two logins' existing full separation (own cookie, own session model, own mail template). Both always redirect to the same neutral `?sent=1` confirmation regardless of whether the email belongs to no account or a real one, so nothing about account existence leaks through response branching; the admin variant additionally withholds the token whenever `user.role === 'ADMIN'` (same request, same neutral response, just silently no email — an Admin's password can only be changed via direct server access, `create-user.js`/`set-role.js`, same rationale as the Admin-exclusion in `app/admin/users/page.tsx`'s `deleteUser`/`updateUserRole`), a distinction `GuestUser` has no equivalent of since it carries no role. Both `resetPassword`/`resetGuestPassword` re-validate the token's expiry (1 hour, `RESET_TOKEN_DURATION_MS`) server-side even though their reset-password pages already pre-check it at page load for UX, clear the token pair on success so it can't be replayed, and delete every `Session`/`GuestSession` row for that account, forcibly logging out any device that was using the old password. `resetGuestPassword` additionally marks a still-unverified `GuestUser` as verified as a side effect — successfully receiving and clicking a reset link is equally strong proof of owning the email address as the separate verify-link flow, so this avoids leaving someone stuck freshly-reset but still login-blocked by `loginGuestUser`'s unverified check.

**Linking the two accounts (one-way)**: `User.linkedGuestUserId` (nullable, `@unique`, `onDelete: SetNull`) ties an admin-side account to the same person's `GuestUser`. `linkGuestAccount` ([app/admin/actions.ts](app/admin/actions.ts), form on `/admin/account`) requires an admin session plus the *guest account's* email and password (a guest session in the same browser is not proof — shared devices), uses the guest-login throttle counters (`loginRules(ip, email, 'guest-login')`) so it can't bypass them, refuses unverified accounts and accounts already linked to another `User`, then opens a guest session. Afterwards every admin login — `loginUser` via `createLinkedGuestSession` and the federation callback via `issueLinkedGuestSession` (both in [app/lib/guest-auth.ts](app/lib/guest-auth.ts); verified accounts only, refreshes `lastLoginAt`) — also opens the guest session, and `logoutUser` ends it via `destroyLinkedGuestSession` (only if this browser's guest session belongs to the linked account). **Never add the reverse direction**: a `GuestUser` password can be reset by mail, an `ADMIN` password deliberately can't, so a guest login must never yield an admin session. Unlinking: `unlinkGuestAccount` (admin side) or `unlinkAdminAccount` ([app/mein-konto/actions.ts](app/mein-konto/actions.ts), the guest decides over their own account). Deleting a `GuestUser` clears the link via the FK. Tests: [tests/e2e/account-link.spec.ts](tests/e2e/account-link.spec.ts).

**Switching between the two logins**: `User` (admin) and `GuestUser` (Nutzer) stay fully separate on purpose (own cookie names `__Host-session`/`__Host-guest-session`, own session models; the optional link above only opens both sessions at once) — but because the cookies are named differently, both sessions can be simultaneously valid in the same browser once someone has logged into each once, with no conflict. `app/admin/page.tsx` calls `getCurrentGuestUser()` alongside `getCurrentUser()` (and `app/mein-konto/page.tsx` calls `getCurrentUser()` alongside `getCurrentGuestUser()`) purely to decide whether to render a "🔀 Mein Konto"/"🔀 Admin-Dashboard" switch link in that dashboard's header — the link is a plain same-origin navigation (not a login), so it only ever appears when the *other* session is already active, staying invisible for the majority of accounts that only use one side. This matters most inside the installed PWA, where there's no address bar to type the other URL into: the shared [app/manifest.ts](app/manifest.ts) also declares `shortcuts` for `/admin` and `/mein-konto` so supporting platforms (e.g. Android/Chrome via icon long-press) can jump directly into either area. Both login pages additionally cross-link to the other one (`/admin/login` → `/mein-konto/login` and back) for discoverability before either session exists yet — e.g. a Moderator who doesn't yet have a Nutzer-Konto for some other Reihe they attend as a guest. The landing page ([app/page.tsx](app/page.tsx)) resolves both sessions the same way and points each button straight at `/admin`/`/mein-konto` (skipping the login page and showing the account's email in the label) whenever that session is already active — this matters specifically for the PWA, where the global footer's Impressum/Datenschutz links are often someone's first tap and previously dead-ended at a login prompt even for an already-authenticated user, since the two `Link`s used to be hardcoded to the `/login` routes regardless of session state (a real bug fixed once already — don't revert those two links back to unconditional hrefs).

**GDPR/DSGVO compliance**: [app/datenschutz/page.tsx](app/datenschutz/page.tsx) is `force-dynamic` and reads both the `IMPRESSUM_*` env vars (same as [app/impressum/page.tsx](app/impressum/page.tsx)) and `SMTP_HOST` at request time, so the published text always names the actual controller and the actual mail-processor host rather than a generic claim — keep it that way if you add another externally-processed data flow (name the concrete env var/host, don't just assert "a provider"). A global footer in [app/layout.tsx](app/layout.tsx) links to Impressum/Datenschutz from *every* page, including the guest-facing RSVP/registration forms that never route through the marketing landing page — Art. 13 GDPR requires that information be reachable at the point of collection, not just from an unrelated homepage a guest may never visit. `RsvpForm` shows a visible notice above the form whenever the effective `isGuestListVisible` is on (passed in explicitly by both `app/[slug]/page.tsx` and the series Termin page — it isn't part of `formConfig`), and a short consent-clarifying note next to the `askAllergies` field, since dietary/allergy data can constitute special-category health data under Art. 9 — both must keep being threaded through if you touch either call site. Self-service erasure (Art. 17) exists at two independent levels matching the two identity systems: `deleteMyParticipantData` in [app/actions.ts](app/actions.ts) (public, takes only an `editToken`, deletes one `Participant` and *all* of its `Rsvp` rows — which for a series-shared `Participant` means every Termin of that series, not just the one currently being viewed; [DeleteMyDataButton](app/[slug]/delete-my-data-button.tsx)'s confirm dialog wording changes based on an `isSeriesShared` prop to warn about this) is rendered on every RsvpForm state (the initial form and all four post-submit screens) whenever a real, persisted `editToken` is in scope; `deleteGuestAccount` in [app/mein-konto/actions.ts](app/mein-konto/actions.ts) (requires a live guest session) is the account-wide equivalent — deletes every `Participant`/`Rsvp` linked via `guestUserId` across *all* series, every `GuestUserSeries` membership, every `GuestSession`, then the `GuestUser` itself, and clears the cookie. Neither deletion path touches the *other* identity system, so a guest with both an anonymous editToken and a "Mein Konto" account needs to use whichever action matches what they actually want erased.

**Self-service password/email change (while logged in)**: distinct from the forgot-password flows (#13, which explicitly exclude `ADMIN`-role `User` accounts) and from `create-user.js`/`set-role.js` (the server-access-only path an Admin's own credentials otherwise depend on) — `changePassword`/`requestEmailChange`/`cancelEmailChange` in [app/admin/actions.ts](app/admin/actions.ts) (`/admin/account`, `/admin/confirm-email`) and their `GuestUser` mirrors `changeGuestPassword`/`requestGuestEmailChange`/`cancelGuestEmailChange` in [app/mein-konto/actions.ts](app/mein-konto/actions.ts) (`/mein-konto/account`, `/mein-konto/confirm-email` — moved off the main `/mein-konto` dashboard after initial user feedback that account management crowded out the actual Reihen/Termine content; both the admin and guest sides now use the identical "⚙️ Konto-Einstellungen" label/icon for this sub-page so the two systems read consistently) are deliberately available to **every** role including Admin. The reasoning: the forgot-password exclusion exists because a compromised mailbox alone must not be enough to take over an Admin account; these actions instead require re-entering the *current* password while already holding a valid session — a compromised mailbox alone satisfies neither condition, so the original threat model doesn't apply here, and there was no reason found in this codebase's history to exclude Admins from either action. Password changes hash and store immediately and invalidate every *other* `Session`/`GuestSession` for that account (`token: { not: currentToken }`) while leaving the current one alone, so changing your own password doesn't log out the device you're using. Email changes are two-phase and never mutate `email` directly: `pendingEmail`/`emailChangeToken`/`emailChangeTokenExpiresAt` (same nullable one-token shape as the reset-token fields on both models) stage the new address, a confirmation link mailed to *that new address* (`sendEmailChangeConfirmation`/`sendGuestEmailChangeConfirmation`) leads to a page whose "Neue Adresse jetzt bestätigen" button (`confirmEmailChange`/`confirmGuestEmailChange`) actually flips `email = pendingEmail` (see "Mail links never act on GET" below) — the old address keeps working for login the entire time a change is pending, and `cancelEmailChange`/`cancelGuestEmailChange` let the account holder abort a pending change from the account page without needing the link at all.

**Account security & federation** (both login systems; code in `app/lib/{auth,guest-auth,password,tokens,throttle,suite,suite-flow}.ts`, routes in `app/api/suite/` and `app/.well-known/suite-identity/`). Rules a new auth-touching change must keep:
- **Tokens are hashed at rest.** `Session.token`, `GuestSession.token`, `User`/`GuestUser` `resetToken`, `emailChangeToken` and `GuestUser.verifyToken` hold `hashToken(plaintext)` (SHA-256, `app/lib/tokens.ts`); the plaintext exists only in the cookie or the mail link. Every creation site passes the plaintext to the mail function separately (`sendPasswordResetEmail(user, token)` etc. — the DB row no longer has it) and every lookup hashes the incoming token first. `Participant.editToken`/`Participant.verifyToken` (event-level bearer links, not account credentials) intentionally stay plaintext. `migrate-token-hashes.js` (run by the Dockerfile CMD, guarded by SQLite `PRAGMA user_version`) converted existing rows once — never run it twice, it would double-hash.
- **Throttle by *reserving* an attempt before verifying** (`reserve()` in `app/lib/throttle.ts`: atomic increment, IP rule first then e-mail rule, `refund()`/`clearFailures()` on success). Check-then-record lets N parallel requests all pass the check. Applied to both logins, password reset requests, guest registration (mail flood) and the "current password" prompt of change-password/change-email. Never add a permanent account lockout (it would let anyone lock out anyone).
- **Timing/enumeration:** unknown e-mail (or an account without a password) runs `verifyAgainstDummy()` and returns the identical error. Reset requests always answer `?sent=1`, even when throttled.
- **Password policy is server-side** (`validatePassword` in `app/lib/password.ts`: ≥10 chars, ≤72 bytes for bcrypt, no trivial values); the HTML `minLength` is only UX. New hashes use bcrypt cost 12, older ones are re-hashed on the next successful login.
- **Cookies use the `__Host-` prefix in production** (no `Domain`, `Secure`, `Path=/`) so a sibling subdomain of the suite can't plant a session cookie. `TRUST_PROXY_HOPS` decides which `X-Forwarded-For` entry counts as the client IP (counted from the right); it must be *measured* per deployment (behind Cloudflare + Nginx Proxy Manager it is 1).
- **Cron routes** must reject an empty/missing `CRON_SECRET` and compare with `safeEqual` — `secret !== process.env.CRON_SECRET` lets `?secret=` through when the env var is empty.
- **Headers** (`next.config.ts`): event slug pages (`/:slug`) are deliberately embeddable (`frame-ancestors *`, used in a CMS iframe); `/admin`, `/mein-konto` and `/api/suite/*` are not. Later header rules override earlier ones for the same key, and `/admin` also matches `/:slug`, so the DENY rules must stay *after* the slug rule.
- **Account link is one-way** (admin login → guest session, never back; see "Linking the two accounts").
- **Federation** is admin-`User`-only (`GuestUser` never takes part) and optional: without `SUITE_SIGNING_KEY`/`SUITE_IDPS` there is no button and no endpoint (the well-known route 404s). Identity is `ExternalIdentity(issuer, subject)`, never the e-mail; a federated login whose e-mail already belongs to a local account is *refused* (`email-taken`), linking happens deliberately from `/admin/account` in an existing session. The provider only vouches for accounts that have a local password (`passwordHash != null`) — no chains. `autoProvision` should stay `false` for rsvp-app (only admins create Creator accounts, see above). After a login that continues into `/api/suite/authorize?…`, the server action redirects to `/admin/login/weiter`, a tiny page doing a real `window.location.replace` — a client-side router transition into a route handler that itself redirects cross-origin hangs. Errors in `/api/suite/callback` during *linking* (`mode: 'link'`, e.g. `linked-other`) go to `/admin/account?error=…` while a session exists — `/admin/login` would immediately redirect a logged-in user and the message would never show; without a session they stay on the login page. See the suite-kit README for the protocol.
- **`requireGuestUser` must check where an `editToken` belongs.** `submitRsvp` takes `editToken` straight from the form, so "a token was sent" proves nothing. The account requirement is only waived for a token that resolves to a `Participant` of THIS series (`existingParticipant.seriesId === event.seriesId`) or, for a standalone event, one that already has an `Rsvp` for it (people who took part before the event was switched to accounts-only). A made-up token, or a valid token from another (open) event, used to slip past the gate, create a new `Participant` and yield a check-in QR code. `performRsvpSubmission` enforces this after resolving `existingRsvp`; keep it there and never derive identity from a form field.
- **The event/series PIN must be enforced wherever a event is reachable by ID, not only when rendering the page.** It used to be checked only in the `page.tsx` files, so anyone who knew an event ID (it sits in a hidden field of the PIN form itself) could call `submitRsvp` directly, download `/api/ical/[id]` (title/location/description), get the `pollUrl` from `/api/poll-link/[eventId]`, or register an account for the series - and a series membership even allows answering through `/api/v1/` without a PIN. All of these now go through [app/lib/pin.ts](app/lib/pin.ts) (`hasEventPinAccess`/`hasSeriesPinAccess`, series PIN authoritative for series Termine; `tokenBelongsToEvent` lets the personal link from a confirmation mail still work). `performRsvpSubmission` checks it itself; only the client API passes `skipPinCheck: true`, because it has already verified the caller's `GuestUserSeries` membership. A new public action or route that takes an event/series ID must call these helpers (the tool redirect routes do so via `resolveToolLinkAccess`). `verifyEventPin` is throttled (`pinRules`: per IP+target and per target) and compares in constant time, because PINs are often 4 digits.
